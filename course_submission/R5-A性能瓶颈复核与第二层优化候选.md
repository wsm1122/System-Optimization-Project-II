## 1. 范围、证据与计时口径

项目根：`${PROJECT_ROOT}`。以下代码、配置和结果路径均以该目录为根，不使用其他数据集。主证据为 R4 正式运行 `results/course_20261121T153154Z_147dfac4/`，下称 `RUN/`。本次仅用标准库读取、分组统计已有 JSONL/CSV，以及查看源码；没有导入推理模块执行模型。

环境沿用 R4：RTX A6000、PyTorch 1.13.0+cu117、FAISS 1.7.2；1798000×256 的 AISHELL train 检索库；IVF4096/PQ64×8，nprobe=32，k=1024，lambda=0.5、temperature=1。当前冻结参数未改变。

必须区分三类量：

1. **无模块插桩请求时间**：`engine.py:156` 请求前同步，随后从 loader 建立及取样开始计时，经过特征拷贝、推理、文本构造，末端 CUDA 同步后结束。包含请求内 CPU 开销，不含模型/索引加载。这里不是没有任何同步，而是没有逐模块同步 hooks。
2. **同一请求的 CPU 前处理区间**：`engine.py:158`–`160`，包含单条清单写入、Dataset/DataLoader 创建、取样、音频读取与特征处理；不含后续 `.to('cuda')`。它是真实请求的子区间，但不能将整个区间称为纯音频读取或纯 fbank。
3. **另一次同步插桩运行**：`engine.py:178`、`runtime_hooks.py:53`、`profile_core.py:30`。每个 hook 前后同步；复合 process 包含 Search/聚合/融合及内层 hook 的同步开销。不能把这些分项相加当作真实请求，更不能用同步 Encoder/无插桩请求计算时间占比。

每组每音频热身 2 次、正式 6 次，6 条音频，即每配置 36 条请求；独立统计单位是音频，不是 36 个重复请求。数据是同一热进程共享模型及索引的交替测量，不是 36 个独立进程。以下均值对每音频相同重复数等权。同步局部方法计时不是独立 FAISS 原生算子微基准；R4 也没有保存逐 CUDA kernel 时间线。

## 3. 热点与真实执行路径

### 3.1 CPU 请求准备与输入传输

`engine.py:79` 的 loader 每次写清单、创建 Dataset/DataLoader，`num_workers=0`；性能循环 `engine.py:159` 对每个请求重建。`vendor/wenet/dataset/processor.py:143` 读音频，`:253` 的 fbank 路径做特征计算。`engine.py:96` 将特征和长度传到 CUDA；该传输属于请求时间，不属于前处理记录，目前没有独立 H2D 计时。DataLoader 构造未显式开启 pin_memory，`.to()` 也未要求 non_blocking；这不足以证明 PCIe 是瓶颈。

### 3.2 Encoder、查询与搜索

`vendor/wenet/transformer/asr_model.py:381` Encoder，`:390` 取 key，`:396` CTC log_softmax。key 已是设备张量。`vendor/wenet_knn_ctc_model.py:208` 搜索整个话语的查询批，GPU 模式不执行 `queries.cpu()`；同设备结果的 `.to(self.device)` 通常是无复制返回，不能计作已证实 D2H/H2D 往返。

`engine.py:49` 附近安装 checked get_knns，先搜索再调用 `retrieval_guards.validate_neighbors`。因此 `runtime_hooks.py:67` 的 faiss_search 包含守卫，现有 1.52 ms 不是纯 FAISS 搜索。`retrieval_guards.py:12`、`:13` 分别读取 GPU 布尔归约的 `.item()`；正常路径有两次主机读取，形成可能的串行同步边界。没有逐算子 trace，不能断言这两次就是主要瓶颈或各自耗时多少。

### 3.3 标签、聚合与融合

`vendor/wenet_knn_ctc_model.py:138`–`141` 在初始化时将 labels 转 long 并常驻目标 GPU；不是每请求重新从 memmap 搬运。`:220` 原始聚合的 CPU zeros→GPU 已被 E3 改为 GPU 直接分配，此处不再作为新候选。其余 softmax、标签 gather、scatter_add、log、nan_to_num 的具体各项时间尚未测出，不能把聚合总时间当作 gather 时间。大输出是 Q×4233，标签/概率为 Q×1024；例如 Q=162 时，仅 FP32 词表输出约 2.62 MiB（理论形状估计，不是峰值测量），完整临时分配与带宽仍需 trace 才能归因。

`:245` interpolate 在 GPU 上重算 argmax、mask、clone、掩码索引与 logaddexp。R4 的 decode_skip_blank=true 在此控制融合掩码，**并没有在 get_knns 前过滤本次实际查询**：process 直接搜索 hidden_states，返回 Q 与编码帧对应。不能沿用“本路径已按 blank 减少搜索量”的结论，也不能在未审查前把新增 blank 查询裁剪作为已证明等价的优化。

### 3.4 解码中的额外主机转换

`vendor/wenet/transformer/asr_model.py:399`–`402` 先计算 CTC top1 并 `.tolist()`，随后在 `knn_args.knn=true` 的 `:408`–`411` 分支，用融合后的 top1 和第二次 `.tolist()` 覆盖先前 hyps 与 scores。`engine.py:70` 附近固定 build_index=false、knn=true；因此正常 kNN 推理有一份被覆盖的主机假设。最后 CPU blank/重复折叠约 0.04 ms，但它不包含前面两次张量转列表、GPU top1 或完整文本构造。不能用 0.04 ms 证明整个解码没有优化空间。

### 3.5 未能定位的硬件原因

本轮没有 SM 利用率、DRAM 带宽、PCIe 传输字节、kernel 时序、分配器 trace 或时钟/温度关联证据。只能确认代码路径和复合区间耗时，不能给出“计算受限”“显存带宽受限”或“PCIe 受限”的最终分类。nvidia-smi 调用位于 `engine.py:167`，在请求计时结束之后；它可能影响后续设备状态，但不是当前记录 request_ms 内的直接计时项。

## 5. 最多三个候选（均未实施）

### 候选一：持久化请求输入管线，消除逐请求装配开销——首选

**源码**：`engine.py:79`、`:142`、`:159`；`vendor/wenet/dataset/processor.py:143`、`:253`。

**证据与边界**：原始 E1 前处理复合区间均值3.380931 ms，六条音频2.6453–4.3198 ms，明确包含每次重写清单、重建 loader 与实际读取/特征计算。尚不知可消除的装配部分占多少；不能承诺节省整个3.38 ms。

**拟议行为**：在独立适配层预先建立本次工作负载的 Dataset/DataLoader，热进程按确定顺序供给请求；避免每个请求写单条临时清单和重建对象，仍按相同音频读取与相同 fbank 配置产生特征。第一步只改变对象生命周期，不同时加缓存、worker、pin memory或异步预取。清单构造移到初始化后，必须分别报告初始化成本、热请求与总任务时间，防止仅把成本移出指标。

**层次**：CPU/应用执行与 I/O 管线层，不涉及模型或检索数学公式，与已有 GPU 输出张量分配不同。

**影响/风险**：理论上不改 CER；但迭代顺序、重复样本、特征随机状态和尾批可能变化，必须验证。常驻 CPU 元数据可能增加，GPU 显存预期无需新增但尚未实测。不得用预计算 GPU 特征替代原始音频输入再宣称同负载加速；若以后评估缓存，必须单独标记场景和冷/热状态。

**所需验证**：授权后先在 dev 拆分清单/对象创建、读音频、fbank 和 H2D，只建立事实基线；随后单变量对比持久 loader，输入特征、长度、覆盖顺序逐条一致，完整 dev 输出一致。两版本都从原音频出发，固定长度分层、平衡顺序，统计无插桩请求与整个任务耗时。若装配只占很小比例，停止该候选而不强称收益。

### 候选二：推迟仅供非 kNN 分支使用的 CTC 假设构造

**源码**：`vendor/wenet/transformer/asr_model.py:399`–`411`；实际调用条件 `engine.py:70`、`:101`。

**证据与边界**：已证实正常 kNN 分支先 `.tolist()` 再覆盖；存在冗余设备到主机转换/等待以及可能的 top1 计算。没有独立记录其时间，不能以 Search 或 CPU collapse 计时替代；它是有明确冗余的数据流候选，不是已测主要瓶颈。

**拟议行为**：只在独立源码副本中将原 CTC 假设计算放入实际需要的建库/非 kNN 分支，使正常 kNN 分支只生成融合后的最终假设；保留原有分支行为、最终 scores、blank 折叠和 token 映射。先证明中间结果没有其他消费者，不改融合概率和 FAISS 调用。

**层次**：CPU/GPU 执行调度、主机转换与冗余工作消除，不是 GPU 输出分配。

**影响/风险**：数学输出应可相同，但移除显式同步可能暴露现有 CUDA/FAISS stream 顺序依赖；R4 有初始化兼容性失败历史，不能把依赖偶然同步的执行当作自动安全。CPU 临时列表可能减少；GPU 峰值与实际延迟方向待测。

**所需验证**：dev 上固定输入，比较 features/encoder/query/IDs/distances/聚合/融合/最终文本及返回 scores；短/长、blank、build_index=false 主路径及保留分支分别检查。先隔离子进程做功能验证，再无捕获计时，必要时 trace 查看 D2H 与同步次数。出现设备错误立即停止，不以重装环境或改变模型绕过。

### 候选三：合并检索合法性守卫的设备归约与主机读取

**源码**：`retrieval_guards.py:12`–`14`，安装点 `engine.py:49` 附近，包络计时点 `runtime_hooks.py:67`。

**证据与边界**：正常路径两个 `.item()` 分支，Search+守卫合计1.523775 ms；尚无证据分别量化纯 FAISS、归约与同步。不能假定1.52 ms全可优化。正常有效返回仍必须完成守卫。

**拟议行为**：计算“非有限距离或非法ID”的组合设备状态，只读取一次；仅在异常路径保留细分诊断，且任何不合法结果都必须在 labels gather 之前拒绝。第一版不用自定义 CUDA，不删除校验，不把错误检查延迟到 gather/scatter 以后。

**层次**：GPU/CPU 同步与执行层；与已有 GPU 分配是不同执行行为，但都属于较低层执行优化，若课程要求更宽层次区分，应优先选候选一而非强称此项是算法层创新。

**影响/风险**：不改合法检索数学结果；可能增加组合状态的小临时量，显存和延迟未测。Python `or`、`and` 或 `bool(tensor)` 可能重新触发同步，不能把表面合并当作实际一次读取。NaN/Inf和非法ID同时出现时应保留明确失败语义，不能只验证正常输入。

**所需验证**：授权后先独立测纯搜索/守卫并保存 kernel 或调用时间线；用真实 dev 邻居以及合成 `id=-1,id=N,NaN,±Inf` 验证拒绝发生在 gather 之前，shape/dtype/空输入的原守卫不变。性能路径不注入异常或捕获CPU张量；再比较完整 dev 输出及无插桩请求。可用既有 Z3 模型说明逻辑契约，但不能替代 CUDA 执行正确性。

## 6. 推荐顺序与后续验证协议（本轮不执行）

**首选候选一，次选候选二，第三候选三。** 候选一有已测同请求复合区间和明确装配代码，且与 GPU 分配层次差别较清晰；候选二数据流上有明确被覆盖结果，潜在改动小，但缺时间证据；候选三对失败守卫敏感，不能为性能削弱保护。

Encoder 虽然是最大的已测同步模块，本轮不提出量化、模型改写、编译或自定义 kernel 候选：没有支撑其开销来源的算子级证据，可能扩大正确性范围。融合约0.55 ms但尚无冗余占比证据，也不作为第四候选。调整 nprobe、索引或近似精度不在首选范围。

后续如获授权：

1. 仅用 AISHELL dev，固定 k=1024/nprobe=32 和模型/字典/库/索引/评分哈希；不更改冻结 test，不启动 test。
2. 先补最小必要分项证据，逐个候选决策，每次只改变一种执行行为；保留可关闭基线。若实测占比太小，允许不实施。
3. 正确性捕获与正式性能分开，float 容差沿用 rtol=1e-5、atol=1e-6，并记录最大误差；IDs/labels/文本严格一致。执行位置/stream 改动需要单独验证，不以CER相同代替张量验证。
4. 固定音频长度分层与ID规则，先冻结工作负载和顺序，不按收益选样本；新 Run ID、热身、至少6次重复、平衡交替。音频级配对均值/标准差/中位数和95% CI；小样本 CI 只用于该工作负载，重复运行不扩充独立样本数。
5. 主指标为无插桩、同定义请求的音频级收益，另报初始化/总任务、RTF、串行吞吐量、CPU资源和PyTorch allocated/reserved及进程显存采样。请求延迟不能混作批处理吞吐；同步区间不得与请求加总。
6. 如果收益不超过波动或 CI 跨零，记录不能确认加速。完整 dev 输出必须一致，任何性能收益都不能以省略合法性检查换取。

## 7. 当前证据不足与最终结论

- 缺少纯 FAISS 与守卫拆分、完整查询准备、H2D、两次 `.tolist()`、GPU top1、gather/softmax/scatter/log 的独立耗时；CPU折叠计时不是完整解码。
- 前处理复合区间有证据，但 loader 装配、磁盘读、页缓存和fbank的比例未知；冷启动/冷缓存未系统评估。
- 缺 CUDA stream/kernel、GPU时钟、PCIe和带宽证据，无法解释同步 Encoder 大于无插桩请求的具体根因，不能将其差异归因于单一硬件因素。
- 六条 dev 音频只覆盖约3–6.5秒，对更长话语、其他硬件、并发服务均无直接保证。
- Top-k 的失败原因在冻结选择规则层面已经明确，但个别替换错误的邻居级原因尚未追踪；不允许用假设补全。

**本阶段结论：第二项优化最值得先调查的是 CPU 请求输入管线，而不是继续缩小 k。另有冗余主机假设构造及守卫同步合并两个有代码证据的备选。三项均未实施，均未获得新的性能或正确性 PASS。R4 原始结果、冻结参数、提交包及官方源码均未修改。**
